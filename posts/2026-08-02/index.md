数年間、個人ブログのメンテナンスと記事更新が止まっていました。

再開するにあたって、新しいリポジトリで一から作り直す選択肢もありました。しかし今回は、同じリポジトリの履歴を残したまま再構築しました。止まっていた期間も含めてこのブログの経緯であり、古くなったプロジェクトを現在の構成へ移す過程も記録として残したかったためです。

## 課題と方針

```timeline
履歴を消さない@リポジトリを作り直さず、更新停止も含むコミット履歴をブログ改善の文脈として保持しました。
基盤を安全に更新する@Next.js・React・Node.jsを段階的に更新し、CI、依存関係の自動更新、セキュリティヘッダーを整備しました。
記事を独立したURLへ移す@クエリパラメータで記事を切り替える構成から、記事・タグごとに静的生成されるURLへ移行しました。
外部での発信も一つにまとめる@Qiita記事は転載せず、初出日・収録日・外部URLを持つメタデータとして一覧へ統合しました。
継続して確認できる形にする@型チェック、lint、production build、E2E、リンク検査を自動化し、更新時に同じ基準で確認できるようにしました。
```

作業前に、次の方針を決めました。

- 公開済みの記事と既存URLをできるだけ失わない
- 依存関係は一度に書き換えず、動作確認できる単位で更新する
- 外部記事は転載せず、実際の初出日とURLを持つ索引として統合する
- 「新しく見せるための日付変更」は行わない
- 見た目だけでなく、CI・SEO・アクセシビリティ・保守手順まで整える

とくに大事だったのは、コンテンツの公開日と、このサイトへ収録した日を別の情報として扱うことです。過去にQiitaへ書いた記事を2026年の記事として表示すれば更新数は増えますが、見る人に誤った時系列を伝えてしまいます。

## 依存関係は段階的に更新した

開始時点の構成はNext.js 14でした。まず元の状態でlint、型チェック、production buildが通ることを確認し、比較できる基準を作りました。その後、セキュリティ修正を取り込み、Next.js 15を中間地点としてからNext.js 16、React 19、Node.js 24を対象に更新しています。

この順序にした理由は、問題が起きたときに原因の範囲を絞るためです。フレームワーク、UI、コンテンツモデルを同時に変更すると、ビルドエラーが移行仕様によるものか、自分の設計変更によるものか判断しづらくなります。

更新後は次を自動で確認します。

```text
npm run lint
npm run typecheck
npm run build
npm run e2e:playwright
npm run check:links
```

依存関係はRenovateで継続的に更新し、本番依存・開発依存ともに`npm audit`で既知の脆弱性が0件になる状態を基準にしました。

## クエリパラメータ中心のブログを、URL中心に変えた

以前はトップページで`?slug=...`を切り替え、Cookieに検索条件を保存して一つの記事を表示する構成でした。操作としては成立しますが、記事単位のURL、メタデータ、静的生成、検索エンジンからの理解という点では複雑です。

新しい構成では責務を分けました。

- `/`：プロフィールと代表的な成果
- `/writings`：ローカル記事と外部記事を横断する検索・一覧
- `/articles/[slug]`：各記事の本文
- `/tags/[tag]`：タグごとの一覧
- `/about`：書いている人と、このブログについて

旧形式のURLへアクセスした場合は、新しい記事URLへ転送します。見た目を変えることより、これまで共有したリンクを壊さないことを優先しました。

## 外部記事を一つの発信履歴にまとめた

Qiitaには2019年から2020年に公開した8記事がありました。これらは本文をコピーせず、タイトル、概要、タグ、初出日、更新日、外部URL、サイトへの収録日をMarkdownのメタデータとして管理しています。

一覧では外部記事であることをバッジとリンク表示で明示します。これにより、読者は同じ画面から過去の発信を探せますが、原典と公開場所は曖昧になりません。

## デザインで優先したこと

デザインは、作品画像を大きく見せるギャラリーではなく、文章と設計判断を読みやすくする技術ブログを目指しました。

- 本文幅を抑え、長い技術記事でも視線移動を少なくする
- 色だけに頼らず、ラベルや文言で外部記事を区別する
- キーボードフォーカスと本文へのスキップリンクを用意する
- アニメーションを減らすOS設定を尊重する
- 小さな画面でも検索、カード、ナビゲーションを崩さない

サイト全体をServer Components中心の実装にし、記事検索もGETパラメータで動作するようにしました。JavaScriptが少ない状態でも、閲覧と検索の主要機能を利用できます。

## 止まっていた履歴もブログの一部にする

結論として、空白期間は隠しません。その代わり、再開時に何を調べ、何を直し、今後どう止まりにくくしたかを示します。

新しいリポジトリから始めれば、完成時点のコードだけをきれいにできます。一方で同じリポジトリを改善すると、古い設計、互換性を保つための判断、段階的な移行まで後から自分でも振り返れます。長く続く個人ブログとしては後者のほうが自然でした。

今後は記事数だけを目標にせず、古い記事の注記更新、一般化できる知見の整理、このサイト自身の定期メンテナンスを続けます。今回の再構築を一度きりにせず、また少しずつ記事を増やしていくための再開地点にします。
