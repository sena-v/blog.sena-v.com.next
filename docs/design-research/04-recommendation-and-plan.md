# 推奨案と実装計画

調査日: 2026-08-02

## 推奨する方向

**A案「年輪 / Editorial Timeline」を主案にし、B案「書斎」の本人性とD案「技術雑誌」の日本語文字組みを限定的に混ぜる。**

比率の目安はA 70%、B 20%、D 10%。これは三つの案を同じ強さで混ぜるという意味ではない。

- Aがページ構造、一覧、線、日付、余白を決める
- Bが編集注記、近況、本人所有の写真や図を足す
- Dが最新記事と長文記事の見出しにだけ強弱を足す

完成後に最初に見えるのは「ポートフォリオ」ではなく、更新日の新しい個人ブログである。読み進めると、発信の継続、技術判断、外部活動が自然に見え、結果としてポートフォリオにもなる。

## 推奨するサイト構成

### `/` — ブログの表紙兼、記事目次

1. `sena-v.` と短い紹介
2. `記事 / このブログについて / RSS`
3. 年へのジャンプ、検索、タグへの入口
4. 全記事の降順タイムライン
5. 外部リンクと小さなフッター

現在の37件は全件表示する。ホームの主役を記事にするため、現在の大型ヒーロー、記事数パネル、3枚のトピックカード、大型CTAは外す。検索フォームを常に大きく見せる必要はないが、隠されたアイコンだけにはしない。

### `/writings` — 道具としての索引

- GETパラメータ`query`を使う検索
- タグ絞り込み
- 公開日の新しい順を既定値にする
- GA4のデータ取得方式が固まった後で「よく読まれている順」を追加
- 人気順でもPV実数と順位バッジは表示しない

トップと同じ記事データを使うが、こちらは探す操作を中心にする。将来100件を超えた場合のページ分割もこの画面から検討する。

### `/articles/[slug]` — 読むための画面

- 題名、概要、公開日、更新日、タグ、掲載元を整理
- 本文幅は日本語32〜40字/行から検証
- 長い記事だけ目次を表示
- 「課題と方針」を含む記事内年表は共通モチーフとして維持
- 古い記事に必要な場合だけ「現在からの注記」を追加
- 前後の記事と同じタグへの導線を末尾へ置く

### `/about` — 副次的なポートフォリオ

ページ名は`Projects`ではなく、現在と同じ「このブログについて」でよい。

1. **現在**: いま扱っている技術や関心
2. **これまで**: 発信とサイトの変遷を短く
3. **代表して読んでほしい記事**: 最大3本、選んだ理由付き
4. **外部**: GitHub、Qiita、必要ならX
5. **このサイトについて**: Next.js、Markdown、公開・計測方針

職務経歴やスキルメーターは載せない。転職時は、このAbout、代表記事、GitHubをセットで案内すれば足りる。

## 初期デザイントークン案

値は方向選択後にブラウザ上で比較し、ここでは役割だけを固定する。

```css
:root {
  --font-body: system-ui, sans-serif;
  --font-meta: ui-monospace, monospace;

  --color-paper: /* 黄みを抑えた白 */;
  --color-ink: /* 黒に近い墨色 */;
  --color-muted: /* 日付と補助文 */;
  --color-rule: /* 年表と区切り */;
  --color-accent: /* 線・リンク・現在年 */;
  --color-note: /* 編集注記 */;

  --measure-body: /* 日本語32〜40字/行を実測 */;
  --measure-wide: /* 記事一覧 */;
  --space-page: clamp(...);
  --space-section: clamp(...);
  --rule-thin: 1px;
}
```

アクセント候補は、深緑、暗い朱、青墨の三つを実ブラウザで比較する。現在の緑を継続してもよいが、ベージュ、角丸、英大文字ラベル、カードを一式で残さない。

## 実装工程

各段階を別コミットにし、途中で方向を修正できるようにする。

### Phase 0 — 方向選択

- A〜Eのうち骨格にする案を決める
- アクセント色3候補と見出し書体2候補を、実ブラウザの小さな比較面で見る
- B案の本人素材を初回から使うか、後日追加にするか決める
- ここで「ホームは全件か最新件のみか」を最終確認する。推奨は現在の全37件

成果物: 選択メモ、除外事項、変更しない要件

### Phase 1 — 基準画面と内容優先順位

- 現行の`/`、`/writings`、代表記事、`/about`をPC・モバイルで保存
- Lighthouse、Core Web Vitals相当、JS/CSS/フォント転送量を記録
- 色もフォントもないHTML優先順位ワイヤーを作る
- 見出し順、ランドマーク、キーボード順を確定

成果物: before画像、性能基準値、4画面の優先順位ワイヤー

### Phase 2 — 土台とトークン

- リセット、本文、リンク、見出し、フォーカスの基礎
- 色、文字、余白、線、行長をトークン化
- Stack、Cluster、Sidebar、Timelineの構成を分離
- システムフォント版を完成させてからWebフォント候補を比較

成果物: 文字だけでも完成して見える共通レイアウト

### Phase 3 — ホームと年表

- ホームをブログ目次へ変更
- 年ごとの`section`と`ol`へ`WritingTimeline`を整理
- デスクトップのsticky年表示とモバイルの通常フロー
- 外部記事、更新日、掲載元を色以外でも識別
- `/writings`の検索・タグ操作を同じ視覚言語へ合わせる

成果物: 全37件を読めるホームと索引

### Phase 4 — 記事とAbout

- 本文幅、見出し、コード、図版、引用、注記を整える
- 長文だけ目次を出す条件を定義
- 記事内タイムラインを一覧と同じ語彙へ合わせる
- Aboutを「現在 / これまで / 代表記事 / 外部」へ再編集
- 外部記事の初出日とURLが維持されていることを確認

成果物: 通常記事、長文、画像あり記事、Aboutの完成状態

### Phase 5 — AIっぽさの脱臭レビュー

AI脱臭を最後の一括作業にせず、この段階で全体を横断して再確認する。

#### 構成

- 巨大ヒーロー + CTA 2個へ戻っていないか
- 数値、3カード、Bento Gridで実績を説明していないか
- 全ページが同じ「小ラベル + 大見出し + カード群」になっていないか

#### 文章

- 抽象的なポートフォリオ語を実在する出来事へ置き換えたか
- 見出しを同じ文型・長さへ揃えすぎていないか
- 本人が普段使わない英語ラベルが残っていないか
- 記事本文の古い語り口を過度に均一化していないか

#### 見た目

- 角丸、影、ピル、グラデーションの用途を一つずつ説明できるか
- 本人と無関係な生成画像やストック素材を置いていないか
- 動きがなくても階層が完成しているか

成果物: PC・モバイルのレビュー画像、修正理由の短い記録

### Phase 6 — 性能・アクセシビリティ・回帰確認

- 320px、モバイル、デスクトップ、200%拡大
- キーボードのみ、Reduce Motion、強制カラー、画像なし
- 見出し構造、リンク名、外部リンク、フォーカス
- LCP 2.5秒以下、INP 200ms以下、CLS 0.1以下を75パーセンタイルの公開目標にする
- デザイン専用Client Component 0、アニメーションライブラリ 0を初期予算にする
- ホーム、索引、代表記事、タグ、AboutのE2Eとリンク確認

成果物: 検証記録、差分画像、公開可否チェック

### Phase 7 — 公開と観測

- Previewで実データ、OG、404、robots、sitemapを確認
- 本番公開後にGA4とCore Web Vitalsを確認
- 人気順はデータが十分に溜まってから別タスクで実装
- デザイン変更と測定結果を記事にし、改修そのものをブログの内容にする

成果物: 公開版、検証記事の下書き、改善バックログ

## 実装時の受入条件

### 内容

- 最新記事が自己紹介や実績数より先に見える
- 外部記事8件を含む全37件を、日付の辻褄を変えずにたどれる
- `Projects`ページがなくても関心と技術判断が分かる
- Aboutの代表記事は3本以内で、選定理由がある

### 見た目

- 年表の線と点がホーム、索引、記事内で一貫する
- 記事行を同寸カードへ入れていない
- 不要な英大文字ラベル、影、角丸、ピルを削減している
- 本人素材がなくても完成して見える

### 読みやすさ

- 日本語本文の行長、行高、見出し余白を実機で検証している
- 320px幅と200%拡大で横スクロールしない
- 色だけで掲載元、更新、リンクを区別しない
- キーボードフォーカスが常に見える

### 性能と保守

- デザインのためだけのClient Componentやアニメーション依存を追加しない
- 画像寸法を予約し、フォント差し替えで大きく動かない
- 通常の記事追加に専用画像や手編集のレイアウトを要求しない
- 配色変更がページ別CSSの上書きにならない

## この順番にする理由

デザイン、AI脱臭、性能を別々の最終工程にすると、後の工程が前の判断を壊す。今回は、内容の優先順位を先に決め、軽いHTML/CSSで年表を作り、各画面で文章と見た目のAI脱臭を行い、最後に実測する。

一方、GA4設定、PV集計、人気順はデザインの前提ではない。同じタイムラインへ後から並び順を追加できるため、今回の方向選択と初期実装を止めずに別タスクとして進められる。

## 次にユーザーが選ぶもの

最初の選択は一つでよい。

> A案を骨格にして進めるか、それともB〜Eのいずれかを骨格に変えるか。

A案を選ぶ場合、その次に初めてアクセント色と本人素材の有無を決める。細部を一度に決める必要はない。
