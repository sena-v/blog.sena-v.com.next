# ブログ改善ロードマップ

最終更新: 2026-08-04

状態: GA4を計測基盤として採用。第5回の構造比較とrefinementを経て確定した[1st最終デザイン・機能仕様](./design-research/round-5-article-cover-engineering/FIRST_FINAL_DESIGN_SPEC.md)を実装し、現在は公開前の安定性・Privacy・運用設定を検証している。

## この文書の目的

このブログを「転職向けに作られたポートフォリオ」へ置き換えるのではなく、これまでの履歴を持つ個人ブログとして育て直す。その過程で、次の四つを無理なく進める。

1. デザインを改修する。
2. 文章・見出し・画面から不自然な「AIっぽさ」を減らす。
3. PVを計測し、数値を公開せずに人気順で記事を探せるようにする。
4. 表示性能を測定し、改善する。

転職時には専用の作品集らしく見せるのではなく、日頃の関心、過去の発信、継続的な手入れが自然に読み取れる状態を目指す。

## 現在地

- サイト基盤の更新と、個人ブログ寄りの画面への修正は `33ece87` までのコミットに保存済み。
- ローカルのCI、ビルド、主要画面のE2Eは通過済み。
- このブランチはまだ `main` へマージも、本番公開もしていない。
- 既存のGA4実装で見つけた初回PVの重複と環境の切り分けは、ローカルで修正済み。本番には未公開。
- 人気順、responsive reader、遅延WebGL外装、縦横切替を実装済み。
- GA4の本番設定確認は後から再開できる状態。現在はデザイン選定を先行する。
- 第1回の5案、第2回の10案、第3回の20案、第4回の20案に加え、記事カバーとWebGL記事ビューアを検討する第5回を [`docs/design-research/`](./design-research/README.md) に保存した。現在は[1st最終デザイン・機能仕様](./design-research/round-5-article-cover-engineering/FIRST_FINAL_DESIGN_SPEC.md)を実装判断の基準にする。

## 変えない前提

- リポジトリは作り直さず、更新が止まっていた期間も含む履歴を残す。
- 外部記事は転載せず、元の公開日、掲載先、URL、取り込み日を持つリンク記事として扱う。
- 記事一覧は新しい順を標準にする。縦線と点を使った年表表現は今回のデザイン選定要件から外し、必要なら記事一覧の一表示候補として後から比較する。
- 「課題と方針」の年表は、独立したプロジェクト紹介ページではなく、通常のブログ記事の一部として残す。
- 過去記事の公開日を新しく見せるために変更しない。実質的な改訂には更新日と追記を付ける。
- PVの実数は、記事一覧、記事ページ、HTML、構造化データ、公開APIに出さない。

## 推奨する進行順

### 0. 現状を基準点として保存する

現在のブログ化、年表一覧、外部記事統合、基盤更新をコミットとして残す。以降の変更は、計測、文体、デザイン、性能の目的ごとに分け、差分と意図を追えるようにする。

完了条件:

- 作業ツリーがクリーンである。
- CI、ビルド、主要画面のE2Eが通る。
- 現時点の画面を比較用に保存できる。

### 1. PV計測を先に開始する

人気順には蓄積期間が必要なので、デザイン刷新を待たずに計測だけを始める。画面にはまだ人気順を出さない。

完了条件:

- 本番だけで計測され、localhostとPreview Deploymentは除外される。
- 正規URL `/articles/{slug}` 単位で集計できる。
- 初回表示とクライアント遷移のどちらも、1画面につき `page_view` が1回だけ送られる。
- 秘密情報がクライアント、リポジトリ、ログへ漏れない。
- 30日程度のデータを貯められる。

### 2. ブログの文体を定義し、第一回の「AI脱臭」を行う

デザイン案を作る前に、既存の本人執筆記事から短い文体ガイドを作る。AI判定器の点数ではなく、本人が普段使う語彙、文の長さ、断定の強さ、具体例、余白の取り方を基準にする。

最初に見直す範囲:

- ヘッダー、トップ、About、記事一覧の説明文
- 2026年の再開記事のタイトル、見出し、導入
- 外部記事の紹介文
- READMEなど、人が最初に読むリポジトリ内文書

原則:

- 過去記事を一括で現代風に書き換えない。
- 「最適化」「価値を提供」「課題を解決」のような抽象語は、具体的な出来事へ置き換える。
- 同じ長さのカード、三項目の対称構成、英大文字ラベルなど、文章以外のAIテンプレート感も対象にする。
- 各実装段階の最後に小さな文言レビューを入れ、最後に全体レビューを行う。

### 3. デザイン前の性能基準を取る

刷新前の状態を測り、デザイン変更による悪化と本来の改善を区別する。ラボ計測だけでなく、公開後は実利用データも見る。

記録するもの:

- Core Web Vitalsの実測値
- LighthouseのPerformance、Accessibility、SEO
- 主要ページのJavaScript量、画像量、フォント量
- トップ、記事一覧、長文記事、タグ一覧の応答と描画

暫定予算:

- 計測スクリプトは遅延読込とし、初期描画を止めない。
- 人気順取得はリクエストごとに外部APIを呼ばず、6〜24時間キャッシュする。
- デザインのためだけの大きなクライアントライブラリを増やさない。
- アニメーションは意味のある箇所だけにし、`prefers-reduced-motion` に対応する。

### 4. デザインを独立したプロジェクトとして調査する

実装へ直行せず、実在する個人ブログや技術ブログ、公開ソース、アクセシビリティ・性能基準を調べる。第1回は年表前提の5案が似た密度になったため、年表とホーム全件表示を外して第2回を実施した。さらに情報設計から異なる20案を作る[第3回調査](./design-research/round-3-variation-first/README.md)を実施し、その10「コンタクトシート」と11「机上のノート」への反応を基に、本人素材を選び、並べ、注記する設計を20方向へ展開する[第4回調査](./design-research/round-4-owned-materials/README.md)へ進んだ。

方向選択後、実装前に追加で確認する情報:

- 好きなブログや雑誌、サイトの参照例
- 明るさ、色、文字密度、写真やイラストの好み
- 「古い」「AIっぽい」「ポートフォリオっぽい」と感じる具体例
- 最も読んでほしい記事と、本人らしいと思う過去記事

各案の比較軸:

- 個人ブログとして自然か
- 本人らしさと時間の蓄積が感じられるか
- 長文が読みやすいか
- 年表表現と新着順を活かせるか
- 保守しやすく、表示性能を守れるか
- テンプレート的、SaaS的、AI生成的に見えないか

第5回では、画像を独立した観察記録ではなく記事カバーとして扱う。カバー指定時は本人素材、未指定時は管理された汎用カバーへフォールバックする。比較の結果、同一比率の中央端末、縦横回転、実DOMの記事reader、右側の小型回転操作、dark mode、scroll可能な記事索引を1st finalとして選び、実記事を使うproduction UIへ統合した。詳細は[1st最終デザイン・機能仕様](./design-research/round-5-article-cover-engineering/FIRST_FINAL_DESIGN_SPEC.md)と[実装検証記録](./design-research/round-5-article-cover-engineering/IMPLEMENTATION_VERIFICATION.md)を参照する。

### 5. 人気順をUIへ加える

十分なデータが貯まった後、記事一覧に「新着順 / 人気順」を加える。標準は新着順のままにする。人気順でもPV数や順位の数字は表示しない。

推奨仕様:

- URLは `/writings?sort=popular` とし、共有・戻る操作ができるようにする。
- まずは直近30日のローカル記事だけを対象にする。
- 同数やデータ不足の記事は公開日の新しい順で安定して並べる。
- 外部記事は自サイトPVを持たないため、最初は人気順の対象外にする。
- 外部記事へのクリックを計測する場合も、PVと混ぜず別の指標として扱う。
- API障害、認証失敗、データ不足時は新着順へ戻し、一覧自体は壊さない。

### 6. デザイン実装後に性能を改善する

基準値との差を見て、効果が大きい順に直す。画像、フォント、不要なClient Component、第三者スクリプト、キャッシュ設定を優先して確認する。

完了条件:

- 基準値より明確に悪化した項目がない、または理由を説明できる。
- 本番のCore Web Vitalsを一定期間確認できる。
- 計測停止時にもブログ閲覧と新着順が動く。
- モバイル、低速回線、キーボード操作を確認できる。

### 7. 最終的な「AI脱臭」と公開レビューを行う

最後に、文章だけでなく画面全体を続けて読み、本人のブログとして違和感がないかを見る。均一すぎる構成、説明過多、意味の薄い英語、過剰な自己評価、実績の羅列を減らす。

公開前には、転職資料としての強さより次を優先して判断する。

- 普通に記事を読みたくなるか。
- 過去から現在への変化が自然に見えるか。
- 誰が何に関心を持って書いているかが伝わるか。
- 更新を再開した後も無理なく使い続けられるか。

## PVを非公開で持つ設計

### 採用案: 既存のGA4を整備して再利用する

このブログではGoogle Analytics 4を採用する。既存プロパティと実装を活かせることに加え、記事別PVだけでなく、検索・SNS・外部サイトからの流入、外部リンククリック、長期的な変化を今後の記事改善へ使えるためである。業務で扱っている知識を自分のサイトで再検証し、実装、検証、結果をブログ改善の記事として残す狙いもある。

構成:

```text
閲覧者
  └─ 本番サイトからpage_viewを送信
       └─ Google Analytics 4（非公開の集計値）
            └─ GA4 Data APIを呼ぶserver-only処理（6〜24時間キャッシュ）
                 └─ [slug-a, slug-b, slug-c] の順序だけを記事一覧へ渡す
```

保持するもの:

- 集計元: GA4の `pagePath` と `screenPageViews`
- アプリ側キャッシュ: 対象期間、生成時刻、並び替え済みslug
- 公開画面: 並び順だけ

保持しないもの:

- 閲覧者の個人識別情報
- 公開用のPV数
- 記事ファイル内のPV
- GitにコミットされたProperty ID、サービスアカウント、秘密鍵
- Data APIの生レスポンスを返す公開エンドポイント

実装前の確認事項:

- 既存GA4プロパティの所有者、Measurement ID、データ期間を確認する。
- 拡張計測の「ブラウザの履歴イベントに基づくページの変更」が無効であることを確認する。
- RealtimeまたはDebugViewで、初回表示と画面遷移がそれぞれ1回だけ計測されることを確認する。
- Google Signalsと広告パーソナライズを利用しない設定を確認する。
- メールアドレスのredactionと、ブログ内検索パラメータ `query` のredactionを有効にする。
- Site Search計測は無効にし、ブログ内検索語を収集しない。
- データ保持期間を14か月に設定する。
- Google CloudでData APIを有効化し、読み取り専用サービスアカウントを用意する。
- Privacyページの内容と実際の設定が一致していることを確認する。

既存実装では、初期化時の `config` とReactのEffect内の `config` が重なり、初回PVを二重送信する可能性があった。現在は `send_page_view: false` で初期化し、App Routerが確定したpathnameだけを手動送信する。GA4管理画面側でも履歴変更page viewを無効にし、検索queryの送信と二重計測を防ぐ。外部リンククリックは拡張計測に任せる。

参考:

- [Google AnalyticsでSPAを計測する](https://developers.google.com/analytics/devguides/collection/ga4/single-page-applications)
- [Google Analytics Data API overview](https://developers.google.com/analytics/devguides/reporting/data/v1)
- [Google Analytics Data API dimensions and metrics](https://developers.google.com/analytics/devguides/reporting/data/v1/api-schema)
- [Google Analytics Data API quickstart](https://developers.google.com/analytics/devguides/reporting/data/v1/quickstart)

### 不採用案: Vercel Web Analyticsを集計元にする

Vercel Web AnalyticsはVercelとの統合が簡単で、cookieを使わない匿名集計が利点である。直近30日の人気順だけなら十分だが、Hobbyでは履歴が1か月に限られ、カスタムイベントとUTM分析にも制限がある。GA4と二重に導入すると計測差、第三者スクリプト、Privacy説明、性能コストが増えるため、現段階では併用しない。

Vercel Web Analyticsは、GA4の運用負担やPrivacy要件が今後合わなくなった場合の移行候補として残す。

参考:

- [Vercel Web Analytics](https://vercel.com/docs/analytics)
- [Vercel Web Analytics pricing](https://vercel.com/docs/analytics/limits-and-pricing)
- [Vercel Web Analytics privacy](https://vercel.com/docs/analytics/privacy-policy)

### 第三候補: 自前のカウンターを持つ

Upstash Redisなどに記事別カウントを保存する方法。サービスから独立できる一方で、bot対策、重複排除、レート制限、保存期間、Privacy、障害対応を自分で持つことになる。単純な人気順のためには責任範囲が大きいため、第一段階では採用しない。

参考:

- [Upstash Redis Vercel integration](https://upstash.com/docs/redis/howto/vercelintegration)

### 必要なら比較する代替サービス

Privacyやセルフホストを優先したくなった場合はPlausibleまたはUmamiも候補になる。ただし新しい契約や運用が増え、PlausibleのStats APIにはプラン上の条件がある。GA4を継続できない理由が生じた場合に比較する。

- [Plausible Stats API](https://plausible.io/docs/stats-api)
- [Umami API](https://docs.umami.is/docs/api)

## 人気順の集計規則

最初の版では、複雑なスコアを作らず次の規則にする。

1. 対象期間は直近30日。
2. Data APIの `pagePath` を使い、`/articles/{slug}` だけを抽出する。
3. 下書き、404、Preview、localhost、管理用URLを除外する。
4. 有効なローカル記事slugと照合し、存在しないものを捨てる。
5. page viewの降順に並べ、同数は公開日の降順にする。
6. 6〜24時間キャッシュし、公開側へはslugの配列だけ返す。
7. 失敗時は公開日の降順へフォールバックする。

データが少ない間に「人気」を断定すると不自然なので、計測開始から30日間はUIを出さない。公開後も利用が少ない場合は、人気順より「よく読まれている記事」など固定の編集選定を使う方がブログとして自然かを再検討する。

## セキュリティとPrivacy

- 分析APIはServer Componentまたはserver-onlyモジュールからだけ呼ぶ。
- GA4 Property ID、サービスアカウント、秘密鍵はVercelのProduction環境変数へ保存し、PreviewとDevelopmentには原則配布しない。
- 公開されるレスポンスに実数、秘密情報、GA4の生レスポンスを含めない。
- pathname以外のURL情報を集計に使わず、検索語や任意クエリを保存しない。
- データ保存期間、削除方法、利用目的を実装時にREADMEまたはPrivacyページへ記録する。
- 分析サービスを変更できるよう、UIはprovider固有のレスポンスへ直接依存させない。

## 実装単位とコミットの分け方

1. `docs`: 計測方式の最終決定とPrivacy方針
2. `feat`: 本番だけの匿名PV計測
3. `test`: route正規化、集計、フォールバック
4. `docs`: 本人の文体ガイド
5. `refactor`: 既存UI文言の第一回見直し
6. `perf`: デザイン前の計測値と性能予算
7. `design`: 候補調査と選択記録
8. `feat`: 選択したデザインと人気順UI
9. `perf`: 実測に基づく改善
10. `refactor`: 最終的な文章・見出し・画面構成の見直し

実装、GA4・Google Cloudの設定、外部への公開は別の判断に分ける。特にサービスアカウント作成、Vercel環境変数、`main`へのマージは、ローカル実装が終わったという理由だけでは行わない。

計測と人気順を公開した後は、次を含む通常のブログ記事を書く。実装前に成果を断定せず、30日間の検証結果を待つ。

- なぜ既存GA4を再利用したか
- 既存コードで見つけた二重計測の可能性
- SPAのpage viewをどう一度だけ数えたか
- Data APIから実数を公開せず人気順だけを作った方法
- 実務で知っていたことと、自分のサイトで再確認できたこと
- 性能、Privacy、運用上のトレードオフ

## 次回決めること

PV実装に入る前:

- 既存GA4プロパティに利用可能な履歴があるか
- Measurement IDと本番環境変数が一致しているか
- 拡張計測、広告向け機能、データ保持期間の設定が方針と一致しているか
- RealtimeまたはDebugViewで二重計測がないか
- Data API用サービスアカウントを作成できるか

デザイン調査に入る前:

- 参照したいサイトと避けたいサイト
- 残したい現在の要素（年表は残す前提）
- 色、書体、情報密度、画像の好み
- 最優先で読んでほしい3〜5記事

## 完了の定義

このロードマップ全体は、次を満たしたときに完了とする。

- ブログとして自然な新デザインが公開されている。
- 本人の文体を基準に、主要なUI文言と新規記事が見直されている。
- PVの実数を公開せず、十分なデータがある場合だけ人気順を選べる。
- 外部分析が停止しても閲覧と新着順が壊れない。
- デザイン前後の性能値が残り、Core Web Vitalsに重大な後退がない。
- CI、E2E、アクセシビリティ、モバイル表示、本番確認を終えている。
- 履歴、外部記事の原典、公開日の整合性が保たれている。
